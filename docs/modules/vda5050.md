# VDA5050 ↔ FIWARE

**Repo:** `vda5050_fiware_repo` · **Image:** `vda5050_fiware:latest` · **Container:** `vda5050_fiware`

The bridge between **VDA5050** AGV communication and the **FIWARE** world. It is an MQTT
client that subscribes to all VDA5050 topics, converts them to the
[FIWARE AMR data model](https://github.com/smart-data-models/dataModel.AutonomousMobileRobot),
and stores them in the [Scorpio context broker](https://github.com/ScorpioBroker) as
NGSI-LD.

## What problem it solves

AGVs speak the **VDA5050** standard (orders & state over MQTT), but the rest of the
system — FIWARE/Scorpio, dashboards, MAPF — wants **NGSI-LD AMR entities**. The bridge is
the translation seam: it converts VDA5050 ⇄ FIWARE AMR both ways so heterogeneous robots
become visible and controllable through one consistent data model. It also guards against
subtle **order-stitching bugs** (sequence-id / orderId / updateId mismatches) that would
otherwise corrupt a robot's order stream.

> In one line: *make any VDA5050 robot visible and controllable through one FIWARE model.*

## Master vs Client

VDA5050 is a master/client protocol. Both sides matter here:

| Side | Who plays it | Responsibility |
| --- | --- | --- |
| **Master** | this bridge (`vda5050_fiware`, see `vda5050_fiware/master.py`) | Issues/stitches **orders**, tracks AGV **state**, and converts everything to the FIWARE AMR model in Scorpio. |
| **Client** | the AGVs — real robots or the [UE5 simulation](/modules/simulation) | Receives orders over MQTT, executes them, and publishes **state** / **connection** / **visualization** messages back. |

The **Master** is the integration brain (and where the order-stitching guards live); the
**Client** is the robot side. The sections below focus on the Master (the bridge);
client behaviour is covered on the [Simulation](/modules/simulation) page.

## Role in the system

```
Client (AGV / UE5 sim) ──VDA5050 over MQTT──► Master: vda5050_fiware ──NGSI-LD──► Scorpio (:9090)
                                                 (order stitching + converter)
```

- Robots (real or [simulated](/modules/simulation)) speak VDA5050 over Mosquitto.
- The bridge converts each message into the FIWARE AMR `StateMessage` (NGSI-LD,
  normalized JSON-LD) and upserts it into Scorpio.
- Downstream, MAPF and the Task Orchestrator read robot state from the context broker.

The launcher's health gate looks for `state` lines in the container logs to confirm the
bridge is receiving robot updates (step 6).

## Prerequisites

On the same Docker network (`rmf2_broker_rmf-network`):

- **mosquitto** — MQTT broker (`:1883`)
- **scorpio** — FIWARE context broker (`:9090`)

## Run

Via the demo launcher (recommended):

```bash
./rmf2_res_vda5050_control.sh start    # or: start_environment_tmux.sh (step 6)
```

Standalone:

```bash
docker compose up -d                   # from vda5050_fiware_repo
```

Or a single container, showing the run command shape:

```bash
docker run -d \
  --name vda5050_fiware \
  --network rmf2_broker_rmf-network \
  vda5050_fiware:latest \
  bash -c "source /colcon_ws/install/setup.bash && \
           ros2 run vda5050_fiware vda5050_fiware mosquitto 1928 http://scorpio:9090 rmf1"
```

## Message mapping

The full VDA5050 JSON-schema → FIWARE AMR mapping is documented in `vda5050-fiware.md` in
the repo. Scorpio uses **NGSI-LD**, so messages are stored in normalized JSON-LD per the
smart-data-models AMR examples.

## Try it directly (send to test)

### 1. Watch the live conversion

```bash
docker logs vda5050_fiware --tail 30 -f      # expect periodic "state" lines
```

### 2. Eavesdrop on the VDA5050 MQTT traffic

```bash
mosquitto_sub -h localhost -p 1883 -t '#' -v       # all topics
# narrow to VDA5050 only (topic prefix varies by deployment):
mosquitto_sub -h localhost -p 1883 -t 'uagv/#' -v
```

### 3. Read what landed in the context broker (NGSI-LD)

```bash
# List AMR entities Scorpio is holding (adjust ?type= to your AMR entity type)
curl -s 'http://localhost:9090/ngsi-ld/v1/entities?type=Amr&limit=5' \
     -H 'Accept: application/ld+json' | python3 -m json.tool
```

### 4. Run the test suite (no live brokers needed)

The repo ships a suite focused on order stitching / sequence correctness — the fastest
way to validate the bridge logic in isolation:

```bash
cd ~/ros_industrial_ws/vda5050_fiware_repo
python3 run_all_tests.py
# individual: test_vda5050_basic.py, test_stitch_guard_*.py, test_order_id_mismatch_bug.py, ...
```

See `STITCH_GUARD_FIXES.md` for the background on the order-stitching guards.

## Troubleshooting

```bash
docker logs vda5050_fiware --tail 50          # expect periodic "state" lines
docker logs rmf2_broker-scorpio-1 --tail 50   # confirm Scorpio is accepting upserts
```

If robots never appear in the context broker, check that the bridge can reach both
`mosquitto:1883` and `scorpio:9090` on the shared network.
